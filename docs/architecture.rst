Architecture
============

Lazypod is built using a modern Rust stack designed for responsiveness, portability, and robust interaction with container engines. This document provides a high-level overview of the system architecture.

Core Technologies
-----------------
The application leverages the following key crates:
- **ratatui**: Used for building the Terminal User Interface (TUI). This provides all the layout components, styling primitives, and rendering blocks.
- **crossterm**: Handled terminal manipulation including reading raw input events (keyboard, mouse) and dealing with terminal setup/teardown.
- **serde** & **serde_json**: Crucial for decoding the JSON output generated by both Docker and Podman CLI tools.
- **tokio**: Employed to manage asynchronous event handling and concurrency without blocking the main rendering loop.

Module Overview
---------------
The source code is organized into discrete functional modules:

- ``main.rs``: The entry point. Handles setup (enabling raw mode, configuring the terminal) and invokes the application loop.
- ``app.rs``: Contains the core state management logic (``App`` struct). This module processes all state transitions, handles updates based on input events, and dispatches API calls to the container engines.
- ``ui.rs``: Responsible strictly for rendering the current application state. The ``draw`` function receives the ``App`` struct and calculates the necessary constraints, blocks, lists, and paragraphs to draw the screen.
- ``events.rs``: Provides an abstraction over ``crossterm``'s raw events. It uses a background Tokio task to poll for terminal events (ticks, key presses) and sends them across a channel to be processed by ``app.rs``.
- ``podman.rs``: Contains the ``EngineClient`` trait and its local implementation (``LocalEngines``). This module isolates the interaction with the Docker and Podman CLI executables. It executes commands like ``docker ps --format json``, parses the standard output, and returns strongly-typed Rust structs (e.g., ``Container``, ``Image``).

Data Flow
---------
The application follows a unidirectional data flow pattern common in TUI applications:
1. **Input**: The event loop (``events.rs``) captures user keystrokes or interval ticks.
2. **Update**: The ``App::update`` method evaluates the event, modifying internal state (e.g., updating the ``selected_index``, or triggering a container action).
3. **Data Fetching**: Periodically or based on an action, the ``App`` uses the ``EngineClient`` to fetch current states of containers and images, replacing the cached lists.
4. **Render**: The ``ui::draw`` function reads the latest state from the ``App`` instance and constructs the interface buffers, which ``ratatui`` paints to the screen.

Container Engine Interoperability
---------------------------------
To support both Podman and Docker seamlessly, Lazypod uses a common interface trait (``EngineClient``). Under the hood, the ``LocalEngines`` struct utilizes ``std::process::Command`` to shell out to either the ``docker`` or ``podman`` binaries. The JSON returned by these commands is deserialized using structs annotated with ``#[serde(alias = "...")]`` attributes, masking the subtle structural differences between the two engines (e.g., handling both `Id` and `ID` casing natively).
